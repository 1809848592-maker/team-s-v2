# M3-11 终审

终审由项目负责人以人类会话完成，不调用模型。它表示负责人决定采用或退回交付，审核意见仍为参考。继续使用集中状态机 `pending_final_review → adopted / final_returned`，不增加交付状态。

## 权限与并发

终审按当前 `ProjectMember.role=leader` 检查。模块负责人、项目创建者或平台管理员身份本身不替代项目负责人。任何一名有权限的负责人即可决定，无需其他负责人投票。提交人不能终审自己提交的交付；项目当前只有一名负责人时例外，决定及状态事件明确记录 `self_review=true`。该规则同时覆盖通过、退回和规范不适用裁定。

终审先锁项目，再锁工作流，锁后重新查询成员身份及完整负责人集合。负责人接受邀请也采用项目→邀请锁序，等待后重新读取邀请状态，避免第二位负责人在唯一负责人自审期间同时加入。并发终审仅第一笔成功，后续请求返回409。

## 终审上下文与裁定

`GET /api/projects/{project_id}/deliveries/{delivery_id}/review/final` 对项目人类成员开放，返回交付绑定版本、工作流修订、当前及历史处理记录、`not_adopted` 与 `specification_exceptions` 两个单列列表，以及 `can_decide`、`self_review`、`context_hash`。规范类不采纳即作为“规范不适用/不采纳”交由负责人裁定，不新增成员标注类型。

终审独立读取同项目同模块的旧正式版本意见，不复用普通报告页面500条历史展示上限。重复意见按原意见及处理修订、理由和处理人合并，保留 `related_finding_ids`；代表ID优先使用当前版本意见。意见中的原理由、操作者、时间及重复关联时冻结的依据均保留。处理上限为5000条意见、32MiB上下文，超限明确拒绝，不能截掉规范项再通过。

`POST` 同一地址，需要人类会话和CSRF：

```json
{
  "decision": "approve",
  "comment": "已核对交付及历史处理记录。",
  "expected_revision": 2,
  "context_hash": "GET返回的64位小写SHA-256",
  "spec_rulings": [
    {"finding_id": "GET规范例外项的UUID", "decision": "accept", "comment": "确认该要求不适用。"}
  ]
}
```

- `decision` 为 `approve` 或 `return`；整体退回必须附非空意见。
- 通过时，必须逐条明确裁定当前上下文的全部规范例外项；裁定为 `accept` 或 `reject`，不能提交未知或重复ID。
- 任一规范例外被驳回，最终结果自动为 `final_returned`，即使整体请求写的是 `approve`。每条驳回必须附意见，不能出现无理由退回。
- 总意见和每条裁定意见最多4000字符，不接受NUL；请求拒绝额外字段，身份、自审标记、目标状态不能由客户端指定。
- 工作流修订及上下文哈希必须都与锁内重读结果相同。哈希覆盖成员负责人集合及所有相关标注修订/理由，旧页面不能默许后来新增的规范例外项；陈旧请求返回409，刷新后重新核对。

终审在同一事务内保存不可变 `final_review_decisions` 记录、完整上下文快照、逐条规范裁定、实际人、自审标记及时间，再转换交付状态并追加事件。后续修改旧版本标注不会改写终审时看到的依据。数据库及ORM均禁止修改、删除或清空终审记录。一旦已采用或终审退回，本版本不能重复决定；退回返工重新提交生成新正式版本，旧版本记录保留。

事件仅存决定ID、结果、上下文哈希和计数，不复制意见正文、理由、原文或凭据。人类报告及所属人智能体报告可读取返工意见；智能体报告不会附带完整终审上下文快照，规范裁定按原有本人交付范围过滤，不能借本人新交付读取同模块其他提交人的历史理由或裁定。

## 智能体边界与本项验证

HTTP Bearer不能进入人类终审接口，即使携带所属人Cookie且所属人是负责人也会拒绝留痕。规范裁定和终审为同一受保护原子操作。MCP不提供终审或规范裁定工具，越权未知工具调用拒绝并留痕。

自动测试只使用隔离数据库、固定审核结果或模型替身，终审逻辑没有真实模型调用。完整前端报告和终审页面在M3-14接入，本项不修改前端。M3里程碑最终验收仍按计划执行真实DeepSeek冒烟，真实Key不提交Git。
