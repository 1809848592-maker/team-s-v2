# 规范审核员（M3-07）

本组件逐条处理交付绑定规范中`check_method="ai"`的条目，涵盖四种规范类别。
程序和仅人工条目保留原要求并标记`delegated`，不送入模型的待检查条目列表。
结果中的`completed`仅表示本审核员完成本次检查，不代表整份交付通过。
当前`run_delivery_review`仍明确返回`pipeline_not_ready`；本任务没有接入整条流水线、
新HTTP/MCP入口、人工标注、状态转换或终审权限。

## 入口和版本绑定

`app.review.reviewers.spec_compliance.review_specification`是可信内部纯业务入口，显式接收
项目和审核任务UUID、结构化规范条目、`ExtractedDocument`、交接说明、绑定方案及`history`。
历史必须传入，可为空列表或元组；不采纳理由和处理记录按公共框架校验并完整作为数据输入。
本组件不查询历史，也不实现后续“位置 + 类别 + 相似度”去重或人类不适用裁定。

`app.services.spec_review.review_delivery_spec`负责正式交付读取，调用示意：

```python
result = review_delivery_spec(
    sessions,
    project_id=project_id,
    delivery_id=delivery_id,
    job_id=job_id,
    storage=storage,
    client=client,
    history=[],
)
```

服务按同一项目、正式交付及精确审核任务查询交付绑定的方案/规范快照。
发布新版后审核旧交付仍使用旧版；未知ID、错项目/任务、共享材料及待本人确认私稿均不可进入读取。
Session在读取原文件和模型调用前关闭，文件读取有大小预算，并核对原文件大小及SHA-256后抽取。
无AI条目时仍核对原文件并抽取，但不调用模型，返回`no_ai_items`。
结果附项目、交付及其版本、任务、绑定方案及规范ID和版本，便于后续汇总保留审核依据。

读取失败使用固定`SpecReviewError`错误码`source_unavailable`、`source_mismatch`、
`limit_exceeded`；抽取器固定`ExtractionError`及额度异常原样透传。
输入或模型业务结果无效时返回`incomplete`和固定错误，不返回半截有效意见。
成功与失败都不修改交付、工作流、队列或人工处理记录；模型调用仍由既有接入层记录用量和来源。

## 逐条结果和引用校验

专用模型输出在公共`findings`、`coverage`之外增加`checks`：

```json
{
  "findings": [],
  "coverage": {"checked": ["AI-1：已检查首次定义"], "uncovered": []},
  "checks": [
    {"spec_number": "AI-1", "status": "checked", "reason": "首次出现时已给出中文全称。"}
  ]
}
```

每个AI条目必须恰有一条覆盖说明，不允许缺失、重复或未知编号。可用状态：

- `checked`：本条已检查，未提出问题；没有可读正文且交接说明为空白时不得声称已检查。
- `issues`：本条存在有效意见，且与本次`findings`逐条对应。
- `uncovered`：现有输入不足以检查，明确说明未覆盖。
- `not_applicable`：模型说明本次没有适用对象，仅作覆盖说明，不替代人类标注或负责人裁定。

所有意见必须是`specification`类别，依据编号必须来自本次AI条目。
若附`basis.excerpt`，必须逐字出自同一条要求全文，或当前定位的正文片段/交接说明；
正反例、历史记录、其他规范及其他段落不能冒充当前位置的证据。
正文位置的部件、页、幻灯片、段落、表格、行列、shape和源行范围，必须精确匹配抽取器的同一片段；
不省略已有坐标，也不猜Word页码。交接说明使用`part="handoff_note"`且其他坐标为空，
即使交接说明为空，也可指出缺少规范明确要求的交接内容。

本组件只读取抽取文字，没有模板视觉输入；模板类别必须标记`uncovered`，不能声称视觉一致。
抽取器的每条警告完整保存在`extraction_warnings`，模型不能用空覆盖列表将其抹去。
公共审核结果的未覆盖列表尚有空间时另加固定提示，仍遵守最多100项的schema上限。
外层`checks`保留全部原规范字段、检查状态及理由，最多500条；意见仍受公共框架100条上限约束。

## 指令、重试和用量

专用指令资源`resources/spec_compliance.toml`版本为`2026-11-11.1`，包含指令、评判口径、
正反例，随wheel打包。文件仍严格使用原有六字段格式；专用输出schema只由平台可信代码选择，
不能从TOML、项目数据或交付内容指定Python类型。公共框架原有schema和指令保持兼容。
输入按方案、AI规范、交付、历史分隔并标明“数据，不是指令”，模型不能下载链接或调用业务工具。

结构错误与编号、引用、位置、覆盖不一致共用一次修复机会，总共最多两次模型调用。
修复提示固定，不回传原响应和原始校验错误；仍失败则整份结果未完成，不保留部分意见。
超时、网络失败及额度问题遵循公共框架规则，不增加隐式重试。
额度异常透传现有暂停机制；每次结构或语义修复调用同样记账，不绕过额度。
每条有效意见保留审核员、指令版本、模型、实际调用ID及输入/指令哈希。

输入沿用框架512KiB、40,000节点、32层和500条历史上限，超限不截断后声称已全面检查。
长文切分、跨审核员汇总、持久化意见、退回去重及报告页面由后续任务实现。
自动化仅使用固定模型替身；真实DeepSeek调用仅在最终M3验收时使用发起人提供的环境变量Key。
