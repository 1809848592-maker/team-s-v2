# 交付依据版本与重新提交

M3-12 对应设计第 14.3 节。正式提交时锁定项目，绑定此时最新的方案与规范；智能体草稿在本人确认成为正式交付时绑定。所有审核步骤继续按这两个不可变版本读取依据，后台重试不会切换到新发布的版本。

发布新方案或规范后，交付列表通过 `version_binding` 提供绑定与最新版本号、ID 及差异。已采用的交付显示“依据旧版方案 / 规范”，保持 `adopted`，原文件、终审快照及上游可读范围保持。正在审核的旧交付继续使用原依据；后续重新提交产生新的正式交付并绑定最新版本。

项目负责人可在“任务与交付”点击“要求重新提交”。接口为：

```http
POST /api/projects/{project_id}/deliveries/{delivery_id}/resubmission-requests
X-CSRF-Protection: 1
Content-Type: application/json

{
  "expected_plan_version_id": "页面所见最新方案的 UUID",
  "expected_spec_version_id": "页面所见最新规范的 UUID"
}
```

只允许当前项目负责人的人类会话操作，且目标必须是依据旧版的已采用交付。智能体 Bearer（包括同时携带所属人 Cookie）拒绝并记录审计；MCP 不提供此操作。页面所见版本已变化返回 409，刷新后再核对。

请求、提交人站内通知及事件在同一事务提交。按项目→工作流加锁，同一交付、同一目标版本对的重复请求返回成功而不重复通知；再次发布版本后可针对新目标记录新请求。要求重交不增加交付状态，不撤回采用、不重新运行旧版审核、不改变模块提交权限。历史请求保存在不可变 `delivery_resubmission_requests`；列表展示最近一条，并区分其目标是否仍为当前版本。模块被移除后，历史交付和记录仍可查看，提交权限继续取当前分工。

自动化验证均使用独立 PostgreSQL schema、固定模型响应；真实模型只在 M3 验收时启用。该功能自身不调用模型。
